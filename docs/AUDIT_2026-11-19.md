| **High** | `public/sw.js`, `package.json`: unchanged service-worker source across many distinct app builds | Browser update checks are byte-comparison based; an unchanged SW does not reinstall, leaving the old **offline** app shell cached while live pages refresh. Stamp each built SW with a deterministic hash of HTML + hashed JS/CSS; enforce in CI and live checks. | **Fix in this PR** |
| **High before private integration** | `src/data/catalogue.ts`, `src/data/pageSource.ts`, `docs/SECURITY.md`: no server-side auth or private-media adapter | Directly embedding HF credentials, dataset URLs or personal files in the public application would disclose them. | **Medium** | `.github/workflows/ci.yml`: production browser tests use headless **Chromium only** | iOS Safari, Android WebView, touch gestures, background-resume, memory pressure and storage eviction remain unverified. Add targeted WebKit/Firefox automation and real phone acceptance with long-image fixtures. | Planned |
| **Medium** | `master` has no branch protection; Cloudflare's Git integration deploys on `master` push while CI runs concurrently | A bad direct push can reach production before tests complete. ### Security and data-boundary checks
- The deployed build is a **public synthetic preview**, not a private authenticated library.
- Strict asset-path validation, image MIME/dimensions constraints, unique opaque IDs and rights-evidence model are implemented in `src/domain/validation.ts`; archive-index validation **does not** mean ZIP bytes are actually scanned or imported.
- Offline copied synthetic pages have SHA-256/size receipts and explicit user download/remove controls in `src/data/offlineChapters.ts`; no media is copied automatically.
- React renders titles/tags as text; no `dangerouslySetInnerHTML` or intentional third-party private media access in the audited reader path.
- Existing local progress is per-series and versioned. Import preview and confirmation do not deliberately delete data. This is **not** transactional two-device sync.

## Prioritised roadmap

**R1. Release safety and offline reliability (now).** Land this SW-fingerprint fix, CI tests and live smoke; refresh status docs. Set protection on `master`. Recheck cold offline use across a subsequent *distinct* release; a single build cannot prove update migration.

**R2. Real-device acceptance (before expanding features).** Test Android Chrome and iOS Safari on the five-chapter trial: scrolling, chapter controls, fullscreen/focus, page resume after interruption, downloaded chapters, offline cold start, browser eviction warnings, and the manual JSON backup transfer. Record evidence, performance and screen-reader findings.

**R3. Independent library UX (no HF required).** Favourites/pinned series, per-series personal tags/collections and chapter-completion markers with versioned *local* persistence and export/import support. Keep sample/private modes isolated; avoid a premature global schema migration. Use user feedback to rank features.

**R4. Safe media interface before HF wiring.** Introduce test-only `CatalogueRepository`, `ChapterManifestRepository` and `PrivateAssetResolver` boundaries using explicit fixtures and denied-access scenarios. Design signed/authorised image delivery, per-device cache rules, rights/provenance, rate limits, error handling and release rollback without committing any actual private manga.

**R5. Authenticated private library and sync.** Only after a reviewed per-app auth design and separate owner approval: connect the storage controller, private Hugging Face dataset, revision-controlled catalogue updates, owner-only destructive operations and optional cross-device sync. Test with a disposable private test dataset before real originals.

## Acceptance and limits

An implementation is done only when typecheck, unit tests, production Chromium tests and live Cloudflare fingerprint checks pass; new code never changes real user media as a side effect. The current automated checks do **not** prove iOS Safari behaviour, mobile memory use, secure private-asset access or Cloudflare account settings. Those require additional targeted evidence.

No destructive operations, private media uploads, cross-repository edits or credentials were performed during this audit.
